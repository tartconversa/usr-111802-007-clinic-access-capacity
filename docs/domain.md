# 门诊预约运营业务数据

来源事件有来源编号、事件编号、修订、外部实体、发生时间和观察时间；同一来源同一事件的更高修订替代先前修订。主体映射只在来源与外部标识的组合内有效，无法映射的事件在现有摘要中列为未归属。通用金额是原始事件上的可选数值，不代表利润、节约额或结算结果。

报告发布接口保留报告正文和摘要哈希，相同编号不接受不同内容。业务口径、结论的适用范围和后续变化的影响需要与原始观察区分。

## 排班分析口径（运营可及性）

排班分析只衡量号源是否够用、等待多久、缺口在哪里，不提供临床诊断或治疗建议。分析事件在通用事件结构之上约定 payload 字段；不携带排班字段的旧格式事件仍归通用摘要，不进入排班分析。

### 事件契约

- booking（预约）：`patient_id`、`site`、`day`(YYYY-MM-DD)、`session`、`status`，状态取值 `booked`/`cancelled`/`waitlisted`/`rejected`；`booked` 与 `cancelled` 必须带 `scheduled_at`（ISO 带时区）；可选 `room`、`replaces`。
- room（诊室事件）：`site`、`room`、`day`、`session`、`status=suspended|reopened`，可选 `seats_adjustment`（受影响号源数，缺省时按该诊室该时段的目录号源推定；目录也没有则告警且不调减）。
- visit（到诊）：`patient_id`、`site`、`day`、`session`、`outcome=arrived|no_show`，可选 `appointment_id`（对应预约链根事件的 event_id）。

### 关键口径

1. 预约链与去重：同一次改约既可以用同一 `(source,event_id)` 的更高修订表达，也可以用新事件携带 `replaces` 指向原事件表达。两种方式都折叠为同一条预约链，需求按链计数、患者按 `patient_id` 去重——改约不会变成两位患者的需求；替换目标缺失或成环会产生告警并按独立链处理。
2. 实际可用号源：`实际可用号源 = 计划号源 − 临时停诊净调减`。`suspended` 调减、`reopened` 冲销；诊室事件永远不计入需求，临时停诊不会被解释为需求骤增。调减超过目录号源时按目录上限截断并告警。
3. 未满足需求：当前仍处于 `waitlisted`/`rejected` 链的去重患者数（患者已转为在约后不再计入）；另设 `溢出 = 预约请求链数 − 实际可用号源`，不为负。
4. 等待时间：`预约就诊时刻 − 该链最早请求时刻`，按天计，给出中位数与 P90；仅统计当前为 `booked` 的预约链，等待名单没有就诊时刻，不参与统计。
5. 到诊与爽约：按预约链匹配（优先 `appointment_id`，其次患者加时段），只反映履约情况并用于计算填充率，不改变需求计数。

### 评估快照与复核

`publish_assessment` 保存管理者确认过的评估，冻结发布当时的分析数据、范围（院区/日期/时段）与口径版本（`scheduling-1`）；相同编号不接受不同内容，原始快照永不被后续补录改写。

后续补录的取消、改约或诊室状态通过事件修订进入，只改变当前分析。`reassess` 逐槽位比对快照与当前数据，列出每个发生变化的字段（旧值、新值、业务原因），并给出该评估是否仍适合继续用于排班的结论与排班影响说明；口径版本升级也会标记旧评估失效。
